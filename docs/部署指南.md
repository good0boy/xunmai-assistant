# 内网部署指南

面向自建内网服务器（不走 publish-mcp）。目标是 `docker compose up -d` 就能跑。

---

## 1. 硬件与依赖

| 项 | 建议 | 说明 |
|---|---|---|
| CPU | 4 核以上 | ONNX 推理 + Qdrant |
| 内存 | 8 GB 以上 | embedding 模型常驻约 400MB，索引全量载入内存 |
| 磁盘 | 30 GB 以上 | 索引 20MB + 模型 92MB + 上传图片 + 日志 |
| 出网 | **不需要** | embedding 模型已随项目打包，LLM 网关除外 |

**embedding 模型已内置**：`backend/kb_src/models/` 里带了一份完整的 HuggingFace
缓存布局（`BAAI/bge-small-zh-v1.5` 的 ONNX 优化版，90.4MB）。
应用启动时会把它拷进可写的缓存目录（`/data/models`），所以**服务器完全不出网
也能跑 dense 检索**。详见 `backend/kb_src/models/README.md`。

## 2. 目录准备

```bash
git clone <你的仓库> xunmai
cd xunmai
cp .env.example .env
```

> **模型目录不在 git 里**（`.gitignore` 排除了 `backend/kb_src/models/`，92MB 二进制）。
> 用 git 部署的话要单独把 `backend/kb_src/models/` 拷过去；
> 直接打包整个目录部署就没这问题。

`.env` 至少要填这些：

```bash
# ---- 模型端点（必填）----
LLM_BASE_URL=http://your-gateway:4000
LLM_API_KEY=sk-xxxx
LLM_MODEL=your-model

# ---- 访问控制（内网部署强烈建议开）----
APP_PASSCODE=给最终用户的入口口令
ADMIN_TOKEN=给管理员的接口令牌
CORS_ORIGINS=http://你的域名:8080    # 不要用 *

# ---- 嵌入模型 ----
FASTEMBED_CACHE_PATH=kb_src/models   # 本地写法；容器内由 compose 覆盖为 /data/models（/kb 只读，缓存须落可写卷）
KB_MODELS_DIR=kb_src/models          # 随包模型源目录；容器内由 compose 设为 /kb/models
HF_ENDPOINT=https://hf-mirror.com    # 兜底：万一要重新下载
```

> `CORS_ORIGINS=*` 时服务端会自动关闭跨域凭证传递（有告警日志）。
> 前后端同源部署时直接写自己的域名即可。

## 3. 构建与启动

### 3.1 本地开发（Windows / 直跑 Python）

前置：`backend/.venv` 已就绪（Python 3.12），依赖见 `backend/pyproject.toml`。

```bash
# 1) 起 Qdrant（只有这一个必须用 docker）
docker compose up -d qdrant

# 2) 首次先建索引（三集合约 11772 块，实测 9 分钟）
cd backend
.venv/Scripts/python.exe -m scripts.build_index

# 3) 起后端（读根目录 .env，端口 8000）
.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload

# 4) 起前端（另开一个终端）
cd ../frontend
npm run dev          # Vite 开发服务器，默认 http://localhost:5173
```

浏览器开 `http://localhost:5173`。接口有鉴权：页面会弹登录框，
口令填 `.env` 里的 `APP_PASSCODE`（为空则不启用）；
直调 API 时带 `X-Admin-Token: <ADMIN_TOKEN>`。

冒烟自检（不依赖浏览器）：

```bash
curl -s http://127.0.0.1:8000/api/v1/health
curl -s -H "X-Admin-Token: $ADMIN_TOKEN" http://127.0.0.1:8000/api/v1/config
```

### 3.2 Docker 部署

```bash
# 首次必须先建知识库索引（三集合约 11772 块，实测 9 分钟）
docker compose run --rm backend python -m scripts.build_index

# 起全部服务
docker compose up -d --build

# 看状态
docker compose ps
curl -s http://127.0.0.1:8000/api/v1/health
```

`health` 返回 `kb_status: ready` 即就绪。`dense_available: false` 表示
embedding 模型没加载（检查 `KB_MODELS_DIR` 是否指向随包模型），
检索降级为纯关键词。

**注意**：`docker compose` 用的是 **Qdrant server 模式**（独立容器），
`backend` 默认 2 个 worker。若改成 local 模式（索引打进镜像），
Dockerfile 会自动把 worker 降到 1 —— Qdrant local 对索引目录是独占锁，
多 worker 会直接起不来。

## 4. 数据卷与备份

| 路径 | 内容 | 是否需要备份 |
|---|---|---|
| `backend/kb_src/` | 语料 + 外部来源 + **embedding 模型** | 需随部署包带走（模型在里面） |
| `data/qdrant/` | 向量索引（三个集合，共约 1.2 万块） | 可重建，但重建要 9 分钟，建议备份 |
| `data/models/` | embedding 模型运行时缓存 | 不用备份，删了会从 `kb_src/models` 重新拷 |
| `data/app.db` | 会话、消息、引用、kb_meta | **必须备份**（用户历史） |
| `data/uploads/` | 用户上传的舌象/面色图片 | 建议备份 |
| `data/reports/` | 建库与评测报告 | 不重要 |

备份：

```bash
tar -czf xunmai-backup-$(date +%F).tar.gz data/app.db data/uploads data/qdrant
```

恢复时把文件放回原位即可（索引可选择一起恢复，或重新 `build_index`）。

**首次建库**（三集合共约 1.2 万块，9 分钟）：

```bash
docker compose run --rm backend python -m scripts.build_index
# 只想补建某几组：
docker compose run --rm backend python -m scripts.build_index --groups classics,judges
```

## 5. 反向代理（Nginx）

**SSE 必须关缓冲**，否则前端会退化成「等生成完一次性显示」：

```nginx
server {
    listen 80;
    server_name your.domain;

    location /api/v1/chat/stream {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Connection '';
        proxy_buffering off;          # 关键
        proxy_cache off;
        chunked_transfer_encoding on;
        proxy_read_timeout 300s;      # 生成可能超过 60s
        proxy_send_timeout 300s;
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

验证代理没缓冲：

```bash
curl -N --max-time 20 http://your.domain/api/v1/stream-probe
```

**逐条滚动出现 = 代理无缓冲**；7.5 秒后一次性全出来 = 缓冲没关掉。

## 6. 访问控制

**默认不启用鉴权，所有人可用**（`.env` 里两项都留空即可，本机/内网信任环境的推荐配置）。

要限制访问时才填（显式配置才拦）：

| 配置项 | 作用 | 谁用 |
|---|---|---|
| `APP_PASSCODE` | 入口口令，`X-App-Passcode` 头 | 最终用户，在登录框输入 |
| `ADMIN_TOKEN` | 接口令牌，`X-Admin-Token` 头 | 运维/脚本调用 |
| `RATE_LIMIT_PER_MIN` | 每 IP 每分钟请求上限（默认 20） | — |
| `DAILY_TOKEN_BUDGET` | 每日 token 预算（默认 200 万） | — |

`/api/v1/health` 与 `/api/v1/config` 永远公开，前端要靠它们判断是否弹登录框。

> 限流是**进程内**计数。多 worker 或多副本部署时，实际限额是配置值的倍数，
> 需要精确控制就在 Nginx 层加 `limit_req`。

## 7. 日常运维

```bash
make logs          # 看日志
make restart       # 重启
make eval          # 检索评测
make test          # 后端单测
cd frontend && npm test   # 前端单测
```

**日志里已带的分段耗时**（`chat done` 事件）：
`retrieval_ms` / `embed_ms` / `search_ms` / `rerank_ms` / `elapsed_ms`。
排障时先看这几个数就能分清是检索慢还是模型慢。

## 8. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 首页能开但点发送没反应 | 反代开了缓冲 | 见第 5 节，`proxy_buffering off` |
| `kb_status: stale` | 代码/词典变了但没重建索引 | `make kb` |
| `dense_available: false` | 随包模型没拷进缓存目录 | 看启动日志的「拷贝随包 embedding 模型」；检查 `backend/kb_src/models/` 是否随部署带过去了 |
| 首字节很慢（>5s） | 首次检索在加载模型 | lifespan 已预热，若仍慢看 `embed_ms` |
| 401 | 凭据没带上 | 前端登录框；`/health` 与 `/config` 不需要凭据 |
| 启动日志报「随包模型拷贝失败」 | 缓存目录不可写 | 检查 `data/` 卷权限；不致命，能出网时会自动下载 |
